# LEGO Technic ESP32 — руководство для ChatGPT

Этот файл фиксирует контекст проекта и порядок помощи в рамках проектного чата. Обязательные правила разработки для любых ИИ-агентов задаются в [AGENTS.md](AGENTS.md); подробный процесс GitHub описан в [docs/AI_TEAM_WORKFLOW.md](docs/AI_TEAM_WORKFLOW.md).

## 1. Проект в двух словах

LEGO Technic ESP32 — прошивка на ESP32-WROOM-32 для управления моделью LEGO Technic через собственную Wi-Fi точку доступа и браузерный Web GUI. В проект входят управление DC-моторами, рулевой сервопривод, OLED SSD1306, мониторинг батареи, настройки NVS, WebSocket и OTA-обновление.

Текущий фактический статус всегда проверяй в GitHub, а не считай этот файл заменой живому репозиторию. Сведения о версии и аппаратной архитектуре ниже являются ориентиром, а не живым состоянием: перед изменениями сверяй `main`, `lego_technic_esp32/lego_technic_esp32.ino` и `lego_technic_esp32/hardware_config.h`. Открытые PR и отдельные feature/release-ветки не меняют архитектуру `main` до слияния.

## 3. Правила взаимодействия и выполнения

- Отвечай пользователю на русском, если он не переключился на другой язык. Объясняй конкретно, избегай общих отчётов вроде «всё готово» без перечисления результатов.
- Если пользователь говорит продолжать уже согласованный план, продолжай со следующего незавершённого шага; не переспрашивай уже подтверждённые параметры и не дублируй выполненную работу.
- Один агент выполняет изменения в рабочей ветке. Второй человек или агент может независимо проверить репозиторий и diff, но не должен параллельно писать в ту же ветку.
- Для функциональной работы используй отдельные ветки и PR, если это соответствует задаче; небольшие документальные правки допускаются напрямую в `main` по явному поручению пользователя.
- Не предполагай, что защита `main` или обязательные PR-checks включены: сверяй фактические настройки и действующие workflow.
- Не запускай GitHub Actions вручную без прямого указания пользователя. Дополнительная ручная программная регрессия перед релизом: `python3 tools/run_regression_checks.py`.
- Разделяй результаты: «проверено по коду», «проверено CI», «проверено на реальном устройстве». Одно не следует из другого.
- Если действие невозможно из-за прав интеграции, скажи об этом и выполни всё доступное; не утверждай, что настройки GitHub были изменены, если они только прочитаны или проверены пользователем вручную.
- Не обещай выполнять работу в фоне. Завершай текущий шаг реальным результатом, ссылкой на PR или конкретным ограничением.

## 4. Правила версий

Для каждого PR используй ровно одну GitHub Label:

| Label | Смысл | Пример для текущей beta |
|---|---|---|
| release:none | Только документация, CI или инструменты без нового бинарного релиза | 0.9.2 beta не меняется |
| release:patch | Исправление или улучшение существующего поведения | 0.9.2 → 0.9.3 |
| release:minor | Новая совместимая функция | 0.9.2 → 0.10.0 |
| release:stable | Первый стабильный выпуск при готовности проекта | 0.x.y → 1.0.0 |
| release:major | Несовместимое изменение после перехода на стабильную версию | 1.x.y → 2.0.0 |

Сама по себе масштабность рефакторинга не означает MAJOR. До выхода 1.0.0 скрипт специально запрещает release:major; для первого стабильного выпуска применяется release:stable. Каждый PR, включая release:none, должен содержать ## Changelog хотя бы с одним пунктом. Подробности сверяй с [docs/release-versioning.md](docs/release-versioning.md).

После слияния проверяй фактический результат `release-versioning.yml`, если он относится к задаче. Не предполагай наличие отдельного служебного PR: текущий workflow определяет способ обновления состояния. Не редактируй `.github/release-automation/state.json` вручную.

## 5. Проверки и генерация

Среди проверок проекта используются:

    python3 tools/project_auditor.py
    python3 tools/test_release_automation.py
    python3 tools/test_calibrate_battery.py
    node tools/test_battery_warnings.js

Для прошивки полагайся на обязательный CI в GitHub Actions. Web GUI, HTML для Pages, README и CHANGELOG частично синхронизируются генераторами в tools/; ищи источник до ручного изменения производных файлов.

В `main` используются workflow `ci-build-deploy.yml`, `release-versioning.yml` и `publish-release.yml`. Отдельных `pull-request-validation.yml` и `release-metadata-validation.yml` нет. Не называй проверки обязательными, пока это не подтверждено фактическими настройками репозитория. Не запускай Actions вручную.

## 6. Аппаратные оговорки

Компиляция и статический анализ не доказывают работоспособность конкретной проводки. При изменении аппаратной схемы проверяй актуальную схему и фактическое подключение. До стендовой проверки всегда обеспечивай физическое отключение питания моторов. Не заявляй, что драйвер, токовая нагрузка, поведение при обрыве I²C или остановка при потере связи проверены, если испытаний не было.

Открытый draft PR с переходом на PCA9685/Adafruit Motor Shield нельзя считать частью текущей архитектуры main, пока он не слит и не проверен на оборудовании.

В исходниках прошивки и bootstrap могут присутствовать значения паролей по умолчанию. Поскольку репозиторий публичный, считай закоммиченные значения публичными; не переноси их в новые документы и не делай их постоянными рабочими секретами. При изменении OTA/Wi-Fi-доступа проверяй совместимость основной и bootstrap-прошивки и возможность восстановить доступ.

## 7. Как выглядит хороший итоговый отчёт

Итог должен включать:
- что изменено и зачем;
- ссылку на ветку/PR и факт слияния, если оно состоялось;
- реальные результаты обязательных проверок;
- влияние на версию и релизную автоматику;
- оставшиеся риски и непроверенные аппаратные сценарии.

Не называй незавершённую проверку успешной, не путай PR Label с Git-тегом и не утверждай, что публикация релиза произошла, если workflow её пропустил.
