# Версионирование и выбор типа релиза

В проекте используется формат **MAJOR.MINOR.PATCH** (`X.Y.Z`). Тип выпуска определяет не субъективная «важность» изменений, а их влияние на возможности проекта и совместимость. Так версия отражает смысл обновления, а не только факт очередного коммита.

## Типы релизов и метки GitHub

Для каждого Pull Request нужно выбрать **ровно одну** метку `release:*`. Эти метки обрабатывает автоматизация репозитория.

| Метка | Когда использовать | Как меняется версия |
|---|---|---|
| `release:patch` | Исправления ошибок, небольшие корректировки и рефакторинг без новых возможностей и без изменения внешнего поведения. | `0.9.1 → 0.9.2` |
| `release:minor` | Новые функции и возможности, расширение Web GUI/OLED, новые режимы управления или аппаратные функции, которые добавляют поведение, но не требуют повышения MAJOR после стабильного выпуска. | `0.9.1 → 0.10.0` |
| `release:major` | Несовместимое изменение после выхода `1.0.0`: изменение интерфейсов, протокола, конфигурации или аппаратных подключений, из-за которого существующий пользовательский сценарий перестаёт работать без миграции. | `1.4.2 → 2.0.0` |
| `release:stable` | Осознанный переход проекта из версии `0.x.y` к первому стабильному выпуску `1.0.0`. Это не обычный крупный релиз: нужно подтвердить готовность текущего набора функций и документации. | `0.9.1 → 1.0.0` |
| `release:none` | Документация, комментарии, README, описания проекта и изменения CI/инструментов, которые не требуют нового бинарного файла прошивки. | Версия не меняется. |

## Главное правило для X, Y и Z

- **Z / PATCH** растёт, когда исправляем или полируем уже существующее поведение.
- **Y / MINOR** растёт, когда проект получает новые возможности. Существенная или сложная функция сама по себе не означает MAJOR, если не ломает установленный контракт совместимости.
- **X / MAJOR** растёт после `1.0.0`, когда изменение несовместимо с предыдущим стабильным выпуском и пользователю потребуется миграция, перенастройка или изменение аппаратной схемы.
- **Первый стабильный выпуск** из `0.x.y` оформляется меткой `release:stable` и переводит версию в `1.0.0`.

Пока проект остаётся в `0.x.y`, автоматизация намеренно запрещает `release:major`: для развития beta-версии используются PATCH и MINOR, а переход к стабильному контракту выполняется через `release:stable`. Если правила автоматики будут меняться, это ограничение следует обновить одновременно с документацией и тестами.

**Важность изменения и несовместимость — разные вещи.** Большая переработка архитектуры, которая сохраняет совместимость, обычно относится к MINOR. И наоборот, изменение распиновки или протокола, ломающее существующие сборки после `1.0.0`, может требовать MAJOR, даже если строк кода изменилось мало.

## Примеры для проекта

| Изменение | Метка |
|---|---|
| Исправить перепутанные цвета стрелок движения или дефект расчёта | `release:patch` |
| Добавить новый экран телеметрии, режим управления или новую совместимую возможность | `release:minor` |
| После `1.0.0` изменить распиновку так, что существующую модель нужно переподключить | `release:major` |
| Объявить прошивку первым стабильным выпуском после проверки функций, аппаратной схемы и инструкции | `release:stable` |
| Исправить README или дополнить техническую документацию без изменений прошивки | `release:none` |

Текущая версия проекта на момент составления документа — `0.9.1`. Поэтому типичные следующие результаты: исправление — `0.9.2`, новая возможность — `0.10.0`, первый стабильный выпуск — `1.0.0`.

## Политика публикации GitHub Release

Сборка прошивки и публикация GitHub Release — разные действия. Обычная успешная сборка на `main` сама по себе не создаёт релиз и не требует закреплять отдельную предрелизную версию.

Workflow `.github/workflows/publish-release.yml` публикует новую прошивку после push в `main` только если:

1. В артефакте есть ровно один свежесобранный файл `.ino.bin`.
2. Исходник прошивки из сборки всё ещё соответствует текущему `main`; устаревшая сборка пропускается.
3. Версия в `app.cpp` отличается от версии в родительском коммите. Если версия не изменилась, публикация пропускается.

Таким образом, изменение документации, CI или другой случайный коммит без повышения версии не создаёт новый GitHub Release. Версия повышается отдельно по метке исходного PR (`release:patch`, `release:minor`, `release:major` или `release:stable`); фиксировать постоянную версию для всех предрелизных сборок не требуется.

Отдельный повторный запуск публикации допускается только через поддерживаемое событие `workflow_dispatch`, инициированное `github-actions[bot]`. Это аварийный/повторный путь для явно запрошенной публикации, а не автоматическая публикация каждой сборки. Не запускайте workflow вручную в рамках обычной проверки PR.

Записи changelog накапливаются, а не заменяются при повторном обновлении той же версии. Новые пункты для уже существующей версии добавляются в её раздел; существующая история и дата заголовка сохраняются. Если в подробном changelog уже есть запись с ссылкой на тот же PR, краткая сводка из `app.cpp` не должна дублироваться.

## Требования к Pull Request

1. Выбирать тип релиза по фактическому diff и ожидаемому эффекту, а не по масштабу задачи или числу изменённых файлов.
2. У PR должна быть ровно одна GitHub-метка из списка `release:patch`, `release:minor`, `release:major`, `release:stable` или `release:none`. Одной строки в описании PR недостаточно: автоматизация читает именно метку.
3. В описании PR должен быть раздел `## Changelog` хотя бы с одним пунктом. Пункты должны кратко описывать результат для пользователя. Это требование действует и для `release:none`.
4. Если тип релиза неоднозначен, сначала объяснить предлагаемый вариант и его последствия. Не сливать PR с неразрешённой неоднозначностью.
5. Перед слиянием проверить, что метка соответствует изменениям. Для документации и автоматизации без нового бинарного файла использовать `release:none`, чтобы не создавать фиктивный выпуск прошивки.

## Источник версии и автоматизация

Канонический маркер версии прошивки хранится в `lego_technic_esp32/app.cpp` в строке `CHANGELOG_VERSION`. Workflow выпуска использует метку PR и раздел `## Changelog` для обновления метаданных версии и журнала изменений. Связанные отображаемые версии в README и Web GUI синхронизируются отдельными шагами автоматизации.

Если меняется сама политика версионирования или поведение скрипта выпуска, нужно обновить этот документ и соответствующие автоматические тесты в одном PR.
