## 1. Общая архитектура

ESP32 создаёт собственную Wi-Fi точку доступа. Пользователь подключается к ней смартфоном или компьютером и управляет моделью через браузер.

```text
┌──────────────────┐
│       Смартфон / ПК          │
│   HTML + CSS + JavaScript    │
└───────┬──────────┘
              │ Wi-Fi
              ▼
┌──────────────────┐
│             ESP32             │
│                               │
│  HTTP-сервер и WebSocket /ws  │
│               │               │
│       web_control               │
│               │                │
│   ┌──────┼───────┐   │
│   ▼           ▼           ▼   │
│ motor_control steering  status│
│   │           │           │   │
│   ▼           ▼           ▼   │
│ TB6612 × 2   Servo     OLED   │
│   │                       ▲   │
│   ▼                       │   │
│ DC-моторы A–D     battery_monitor
└────────────────────┘
````

Основные принципы:

* управление через браузер, без отдельного мобильного приложения;

* локальная Wi-Fi сеть, не требующая домашнего роутера;

* разделение прошивки на модули с отдельными зонами ответственности;

* единая конфигурация GPIO и PWM-каналов;

* остановка приводов при длительном отсутствии команд;

* сохранение настроек в энергонезависимой памяти;

* автоматическая сборка прошивки и проверка изменений через GitHub Actions.

### 2.3. PWM и драйверы

| Мотор | Драйвер      | PWM GPIO | LEDC-канал |
| ----- | ------------ | -------- | ---------- |
| A     | TB6612FNG №1 | 18       | 4          |
| B     | TB6612FNG №1 | 22       | 5          |
| C     | TB6612FNG №2 | 23       | 6          |
| D     | TB6612FNG №2 | 1        | 7          |

Параметры PWM DC-моторов:

* частота — 5 кГц;

* разрешение — 8 бит;

* диапазон заполнения — 0–255.

Оба драйвера используют общий `STBY`. При запуске прошивка переводит его в LOW и устанавливает входы направления в безопасное начальное состояние. Управление драйверами активируется через `updateDriverStandby()`.

Аппаратные ограничения:

* GPIO1 обычно используется UART0 TX. Его применение для PWM мотора D может конфликтовать с последовательным выводом и некоторыми сценариями прошивки.

* GPIO32 и GPIO33 заняты мотором D. Использовать их для светотехники нельзя без изменения распиновки.

* Необходимо проверить уровни питания, общую землю и допустимые токи драйверов в реальной сборке.

* Выбранные GPIO и LEDC-каналы нельзя менять без проверки совместимости и обновления документации.

### Правила разделения ответственности

* GPIO и PWM-каналы определяются в `hardware_config.h`.

* Функции управления приводами находятся в `motor_control`.

* Формат входящих команд и события WebSocket обрабатываются в `web_control`.

* HTML-интерфейс хранится отдельно от логики прошивки.

* Измерение батареи и обновление дисплея не должны дублировать логику основного цикла.

* Сохранение настроек выполняется через `preferences_manager`.

* `app.cpp` остаётся точкой координации, а не местом для размещения всей реализации.

При дальнейшем рефакторинге перенос кода должен сохранять поведение системы. Изменение логики управления следует отделять от простого переноса функций между файлами.

### 4\. Режимы управления

Режимы объявлены в `motor_control.h`.

```cpp
enum Mode {
  MODE_TANK = 0,
  MODE_CAR = 1,
  MODE_TEST = 2
};
```

### 4.1. Танковый режим — `MODE_TANK`

Основной сценарий управления двумя сторонами модели:

* A — левая сторона;

* B — правая сторона.

Направление и скорость каждой стороны задаются независимо. Фактическая механическая конфигурация зависит от сборки модели.

### 4.2. Классический режим — `MODE_CAR`

Основной сценарий использует:

* A — тяга;

* S — рулевое управление;

* B — дополнительный привод либо имитация двигателя.

При включённой имитации двигателя в классическом режиме значение мотора B рассчитывается автоматически на основе значения A. Ручные команды B в этом состоянии игнорируются.

### 4.3. Тестовый режим — `MODE_TEST`

Предназначен для настройки и проверки отдельных каналов:

* A, B, C, D — DC-моторы;

* S — сервопривод.

Конкретные доступные элементы управления определяются текущей реализацией веб-интерфейса.

### 4.4. Общие правила

* Значения каналов находятся в диапазоне от −100 до 100.

* При смене режима прошивка вызывает `stopAll()`.

* Настройки реверса привязаны к физическим каналам, а не к выбранному режиму.

* Переключение режима не должно оставлять предыдущие команды движения активными.

### 5\. Управление DC-моторами

Базовая функция управления мостом `setDCBridge()` находится в `motor_control.cpp`.

Для каждого мотора прошивка:

* Ограничивает входное значение диапазоном −100…100.

* Преобразует абсолютное значение в PWM 0…255.

* Выбирает направление с помощью двух входов драйвера.

* Передаёт рассчитанный PWM на соответствующий LEDC-канал.

| Команда                | IN1  | IN2  | PWM                      |
| ---------------------- | ---- | ---- | ------------------------ |
| Положительное значение | HIGH | LOW  | Пропорционально скорости |
| Отрицательное значение | LOW  | HIGH | Пропорционально скорости |
| Ноль                   | LOW  | LOW  | 0                        |

Нулевое значение задаёт LOW на обоих входах направления и PWM 0. Поведение механического выбега или торможения необходимо оценивать с учётом схемы и драйвера.

### 5.1. Реверс

Для каждого мотора предусмотрен независимый флаг:

* `reverseA`;

* `reverseB`;

* `reverseC`;

* `reverseD`.

Реверс меняет знак значения, передаваемого драйверу, не меняя входную команду интерфейса.

### 5.2. Имитация двигателя

При `engineSimOn == true` и `currentMode == MODE_CAR` мотор B получает автоматически рассчитанное значение на основе A:

```text
aux = 33 + 67 × abs(motorAVal) / 100
```

Результат округляется до целого значения. Реверс B учитывается при передаче команды драйверу.

При выключении имитации мотор B сбрасывается в ноль. При включении прошивка повторно применяет текущее значение A.

### 6\. Рулевое управление

Сервопривод управляется через `steering_control.cpp`.

Параметры:

* частота — 50 Гц;

* центр по умолчанию — 1500 мкс;

* максимальный угол по умолчанию — 45 градусов;

* диапазон команды — −100…100;

* диапазон центра, задаваемый триммером, — 1100…1900 мкс;

* диапазон максимального угла — 5…90 градусов.

Расчёт импульса:

```text
pulse_us = center_us
         + (value / 100) × max_angle_deg × (1000 / 180)
```

Результат ограничивается программным диапазоном 500–2500 мкс.

Настройки центра и максимального угла сохраняются в NVS. Реальный угол поворота зависит от конкретного сервопривода и механики модели. Для сервоприводов непрерывного вращения поведение отличается от обычного позиционного сервопривода.

Перед аппаратным использованием необходимо проверить соответствие программных ограничений диапазону, допустимому конкретным сервоприводом.

### 7\. WebSocket и HTTP

### 7.1. HTTP

Прошивка использует `AsyncWebServer` на порту 80.

| Путь    | Назначение                          |
| ------- | ----------------------------------- |
| /       | Основная HTML-страница управления   |
| /ws     | WebSocket-соединение                |
| /update | Интерфейс OTA-обновления ElegantOTA |

Эндпоинт `/calib` временно отключён. Калибровка и настройки передаются через WebSocket.

### 7.2. WebSocket-команды

Команды передаются в JSON.

| Назначение             | Пример               |
| ---------------------- | -------------------- |
| Управление мотором A   | {"ch":"A","val":75}  |
| Управление мотором B   | {"ch":"B","val":-30} |
| Управление мотором C   | {"ch":"C","val":50}  |
| Управление мотором D   | {"ch":"D","val":40}  |
| Управление рулём       | {"ch":"S","val":-25} |
| Переключение режима    | {"mode":1}           |
| Центр руля             | {"trim":15}          |
| Максимальный угол руля | {"maxdeg":45}        |
| Реверс A               | {"revA":1}           |
| Реверс B               | {"revB":1}           |
| Реверс C               | {"revC":1}           |
| Реверс D               | {"revD":1}           |
| Передний свет          | {"ledF":1}           |
| Задний свет            | {"ledR":1}           |
| Имитация двигателя     | {"eng":1}            |

Значения `mode`, `trim` и `maxdeg` проверяются и ограничиваются в обработчике. Команды каналов принимаются только для известных каналов и значений в допустимом диапазоне.

Состояния света пока являются логическими: физическое управление светодиодами не реализовано.

### 7.3. Статус системы

При подключении клиента сервер отправляет текущий статус. Далее статус обновляется примерно раз в секунду.

| Поле           | Значение                                   |
| -------------- | ------------------------------------------ |
| st             | Маркер статуса                             |
| v              | Напряжение батареи                         |
| p              | Расчётный заряд в процентах                |
| r              | RSSI лучшего подключённого Wi-Fi-клиента   |
| m              | Текущий режим                              |
| c              | Количество WebSocket-клиентов              |
| ra, rb, rc, rd | Состояния реверса моторов                  |
| lf, lr         | Логические состояния света                 |
| es             | Состояние имитации двигателя               |
| tr             | Смещение центра руля относительно 1500 мкс |
| md             | Максимальный угол рулевого управления      |

Пример формата:

```json
{
  "st": 1,
  "v": 7.85,
  "p": 75,
  "r": -45,
  "m": 1,
  "c": 1,
  "ra": 0,
  "rb": 0,
  "rc": 0,
  "rd": 0,
  "lf": 0,
  "lr": 0,
  "es": 0,
  "tr": 0,
  "md": 45
}
```

Это пример структуры сообщения, а не гарантированные значения в конкретный момент времени.

### 8\. Безопасность управления

### 8.1. Тайм-аут команд

В `app.cpp` задано:

```cpp
const unsigned long CMD_TIMEOUT_MS = 500;
```

Если команды управления не поступают дольше заданного времени, основной цикл проверяет состояние приводов и при необходимости вызывает `stopAll()`.

Веб-интерфейс использует периодическую отправку актуальных значений каналов, чтобы удерживаемая команда не считалась потерянной только из-за отсутствия движения слайдера.

### 8.2. Функция `stopAll()`

Функция в `motor_control.cpp`:

* выключает имитацию двигателя;

* обнуляет значения A, B, C и D;

* устанавливает нулевые команды на все четыре драйверных канала;

* возвращает рулевое управление к центральному значению;

* обновляет состояние STBY.

### 8.3. Начальная инициализация

При старте:

* STBY устанавливается в LOW.

* Входы направления моторов переводятся в LOW.

* Настраиваются PWM-каналы.

* Инициализируются сервопривод и OLED.

* Загружаются сохранённые настройки.

* Запускается Wi-Fi точка доступа.

* Настраиваются WebSocket, HTTP и OTA.

* Вызывается `stopAll()`.

### 8.4. Ограничения защиты

Тайм-аут команд и `stopAll()` являются программными механизмами защиты, но не заменяют аппаратную проверку. Необходимо проверить поведение при потере Wi-Fi, закрытии браузера, перезапуске контроллера и обрыве питания.

### 9\. Мониторинг батареи и OLED

### 9.1. Измерение напряжения

Реализация находится в `battery_monitor.cpp`.

* GPIO34 используется как аналоговый вход.

* Для одного измерения усредняются восемь показаний АЦП.

* Используется коэффициент делителя `BATT_DIVIDER_FACTOR = 0.2680`.

* Напряжение пересчитывается в вольты.

```text
V_adc = (среднее значение ADC / 4095) × 3.3
V_batt = V_adc / 0.2680
```

Коэффициент должен соответствовать фактическому делителю и калибровке измерений. Перед эксплуатацией показания необходимо сверить с мультиметром.

### 9.2. Расчёт процента заряда

Для расчёта используются опорные точки:

| Напряжение | Заряд |
| ---------- | ----- |
| 6.0 В      | 0%    |
| 6.8 В      | 10%   |
| 7.0 В      | 25%   |
| 7.4 В      | 50%   |
| 7.8 В      | 75%   |
| 8.2 В      | 100%  |

Между точками используется линейная интерполяция.

Процент заряда обновляется только после нахождения модели в состоянии покоя в течение 400 мс. Напряжение при этом измеряется при каждом обновлении мониторинга.

Порог низкого заряда — ниже 6.0 В. Предупреждение формируется после нескольких последовательных низких измерений; отключённая батарея обрабатывается отдельно.

Эти пороги предназначены для текущей конфигурации и требуют проверки с фактическим аккумулятором.

### 9.3. Wi-Fi

Мониторинг получает RSSI подключённых к точке доступа клиентов и использует лучшее доступное значение. Если подключённых клиентов нет или чтение состояния Wi-Fi не удалось, возвращается 0.

### 9.4. OLED

`display_control.cpp` отображает:

* текущий режим;

* процент заряда;

* напряжение батареи;

* количество WebSocket-клиентов;

* предупреждение `LOW BATTERY` при подтверждённом низком заряде.

Дисплей SSD1306 использует адрес I²C `0x3C` в текущей конфигурации.

### 10\. Сохранение настроек

Настройки хранятся в NVS через `Preferences`. Пространство имён:

```text
cfg
```

| Ключ    | Тип     | Назначение                            |
| ------- | ------- | ------------------------------------- |
| revA    | uint8_t | Реверс мотора A                       |
| revB    | uint8_t | Реверс мотора B                       |
| revC    | uint8_t | Реверс мотора C                       |
| revD    | uint8_t | Реверс мотора D                       |
| ledF    | uint8_t | Логическое состояние переднего света  |
| ledR    | uint8_t | Логическое состояние заднего света    |
| steer_c | int     | Центр сервопривода в микросекундах    |
| steer_a | int     | Максимальный угол рулевого управления |

Режим работы и состояние имитации двигателя в текущем `preferences_manager.cpp` не сохраняются.

Правило совместимости: не переименовывать существующие ключи NVS без миграции или осознанного сброса сохранённых настроек.

### 11\. Сборка и зависимости

Сборка прошивки автоматизирована через GitHub Actions.

### Основные зависимости

* Arduino ESP32 Core `2.0.9`;

* ESPAsyncWebServer `3.1.0`;

* AsyncTCP `1.1.4`;

* ArduinoJson;

* Adafruit SSD1306;

* Adafruit GFX Library;

* Adafruit BusIO;

* ESP32Servo;

* ElegantOTA.

Часть библиотек устанавливается без жёстко указанной версии. Поэтому для воспроизводимой сборки следует учитывать фактически установленные версии и проверять совместимость после обновления зависимостей.

Проект использует классический API LEDC, поэтому обновление Arduino ESP32 Core требует отдельной проверки.

### Ручная сборка через Arduino IDE

* Установить ESP32 Arduino Core 2.0.9.

* Установить библиотеки, указанные в workflow сборки.

* Открыть `lego_technic_esp32/lego_technic_esp32.ino`.

* Выбрать плату ESP32 Dev Module.

* Выполнить компиляцию и прошивку.

### OTA

В `app.cpp` ElegantOTA инициализируется с учётными данными по умолчанию. Перед использованием OTA в доступной другим людям сети необходимо заменить стандартные учётные данные и проверить фактические настройки доступа.

### 12\. GitHub Actions и публикация

### `build.yml`

* Собирает прошивку для ESP32.

* Устанавливает зависимости.

* Выполняет компиляцию проекта.

* Содержит шаг публикации бинарного файла для `main`.

В текущей конфигурации автоматический запуск сборки по push в ветке `feature/four-dc-motors` ограничен изменениями в `lego_technic_esp32/**`. Также доступен ручной запуск workflow.

### `extract-gui.yml`

* Извлекает HTML из `web_page.cpp` или, если HTML ещё находится там, из `app.cpp`.

* Обновляет `index.html`.

* Формирует `CHANGELOG.md` по маркерам версии в `app.cpp`.

* Обновляет версию прошивки и ссылку на демо в `README.md`.

* Создаёт коммит с результатами, если сгенерированные файлы изменились.

### `deploy-pages.yml`

Отвечает за публикацию демо на GitHub Pages. Текущая конфигурация публикует изменения из `main` при выполнении заданных условий или по ручному запуску.

Важно: успешная облачная компиляция подтверждает сборку кода, но не гарантирует корректную работу подключённой аппаратуры.

### 13\. Ограничения текущей версии

На момент версии `0.3.3 Refactoring`:

* Четыре DC-мотора вынесены в отдельный модуль, но требуют проверки на реальной модели.

* Работа сервопривода и его диапазоны требуют аппаратной проверки.

* Физическое управление светом не реализовано: `applyLeds()` пока пустая.

* GPIO32 и GPIO33 заняты мотором D.

* GPIO1 используется как PWM мотора D и может конфликтовать с UART0 TX.

* Измерение батареи требует калибровки по фактическому делителю и аккумулятору.

* OLED и мониторинг Wi-Fi требуют проверки на устройстве.

* Эндпоинт `/calib` отключён.

* Поведение при потере связи и восстановлении соединения должно быть проверено экспериментально.

* Публикация релиза не означает завершённую аппаратную валидацию.

### 14\. План аппаратных испытаний

Перед выпуском версии необходимо проверить:

* Моторы A, B, C и D запускаются независимо.

* Направление и скорость каждого мотора корректны.

* Реверс каждого мотора сохраняется после перезапуска.

* Танковый, классический и тестовый режимы работают ожидаемо.

* Имитация двигателя не конфликтует с ручным управлением B.

* Сервопривод работает в допустимом диапазоне и корректно центрируется.

* При смене режима выполняется остановка приводов.

* При потере WebSocket-команд срабатывает тайм-аут.

* После переподключения управление восстанавливается предсказуемо.

* Настройки сохраняются и загружаются корректно.

* Напряжение батареи совпадает с контрольным измерением в допустимых пределах.

* Предупреждение низкого заряда срабатывает корректно.

* OLED отображает актуальное состояние.

* OTA обновляет прошивку без нарушения работы системы.

### 15\. Правила дальнейшего развития

* Не менять GPIO без пересмотра схемы и проверки ограничений ESP32.

* Не менять PWM-каналы без проверки совместимости с используемыми библиотеками.

* Не объединять модули обратно в `app.cpp` без архитектурной необходимости.

* Не дублировать обработку одних и тех же команд в нескольких модулях.

* Не удалять ключи NVS без плана миграции.

* Не считать функцию реализованной только потому, что для неё есть кнопка в интерфейсе.

* После изменений в логике управления выполнять сборку и, если затронуто поведение, аппаратную проверку.

* Не сливать `feature/four-dc-motors` в `main` и не выпускать релиз до проверки реальной модели.

Главный принцип проекта: модульная архитектура должна облегчать развитие и обслуживание прошивки, а документация — точно отражать реализованное поведение, отдельно обозначая незавершённые функции и непроверенные аппаратные сценарии.
