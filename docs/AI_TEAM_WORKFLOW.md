# Рабочий процесс ИИ-агентов в LEGO Technic ESP32

Документ задаёт практический порядок изменения кода, документации, CI и релизной автоматики. Базовые ограничения находятся в [AGENTS.md](../AGENTS.md); контекст для ChatGPT — в [CHATGPT_PROJECT_GUIDE.md](../CHATGPT_PROJECT_GUIDE.md).

## 1. Перед изменением

1. Получи актуальный SHA `main`, проверь текущие workflow, ветки и относящиеся к задаче PR. Не предполагай, что branch protection включена или что у PR есть обязательные checks.
2. Найди связанный исходный код, тесты, генераторы и документацию. Не делай вывод о работающей функции только по названию PR или тексту задачи.
3. Раздели задачу на минимальные безопасные изменения. Аппаратную переработку, исправление CI и обновление документации лучше проводить отдельными PR, если они не являются частями одного неразрывного изменения.
4. Определи тип релиза по реальному эффекту изменений. Сложная архитектурная переработка не автоматически означает MAJOR; важны совместимость и влияние на пользователя.

## 2. Рекомендуемый шаблон PR

Для функциональной работы создай ветку от текущего `main`, просмотри diff и открой PR, если это соответствует задаче. Малые документальные исправления могут вноситься напрямую в `main` по явному поручению пользователя. Не запускай Actions вручную. Если работа проходит через PR, описание должно содержать:

- понятный заголовок с областью и сутью изменения;
- ровно одна GitHub Label release:*;
- раздел ## Changelog с хотя бы одним пунктом даже для release:none;
- описание тестов и оставшихся ограничений;
- для аппаратных изменений — отдельное указание, что именно проверено физически и что ещё не проверено.

Пример описания:

    Release type: release:none

    ## Summary
    - Что изменено и зачем.

    ## Changelog
    - Краткий результат для пользователя.

    ## Validation
    - Локальные тесты и ожидаемые проверки CI.

    ## Hardware validation
    - Не выполнялась / перечислить конкретные завершённые испытания.

Строка Release type: полезна для чтения человеком, но источником решения автоматики служит GitHub Label. Нельзя заменять метку текстом в описании.

## 3. Автоматизация и завершение изменений

- Сверяй ожидаемые проверки с действующими файлами в `.github/workflows/`, а не со старыми названиями в документации.
- Текущий набор workflow: `ci-build-deploy.yml`, `release-versioning.yml` и `publish-release.yml`. Отдельных `pull-request-validation.yml` и `release-metadata-validation.yml` в `main` нет.
- `ci-build-deploy.yml` обрабатывает настроенные push-события и поддерживаемый `workflow_dispatch`; не запускай его вручную без прямого указания пользователя.
- Перед окончательным релизом оставлена одна дополнительная ручная программная регрессия: `python3 tools/run_regression_checks.py`. Она не заменяет аппаратные испытания.
- Не предполагай, что branch protection или обязательные PR-checks включены. Проверяй фактическую конфигурацию, если она важна для текущей задачи.

## 4. Как устроена релизная автоматика

### Источники истины

- Версия прошивки и текущий блок changelog: lego_technic_esp32/app.cpp.
- Логика применения метки, валидации и обработка списка уже учтённых PR: tools/release_automation.py.
- Идемпотентное состояние: .github/release-automation/state.json.
- Политика версионирования: [release-versioning.md](release-versioning.md).
- Техническое описание автоматики: [release-process.md](release-process.md).

Не редактируй производные файлы или состояние вручную вместо исправления источника или генератора. Если меняется поведение автоматики, обнови тесты и соответствующие документы в том же PR.

### Что происходит после слияния исходного PR

1. Workflow Build, Extract and Deploy проверяет/генерирует необходимые файлы, собирает прошивку и при изменениях публикует GitHub Pages.
2. Release Version Automation запускается после успешного main-build и сопоставляет push с исходным PR.
3. Автоматика вычисляет версию и обновляет служебные метаданные через workflow; точный путь изменения и слияния смотри в актуальном `release-versioning.yml`, не полагайся на старое описание metadata PR.
4. Для реального релиза новая сборка запускается отдельно. Workflow Publish Firmware Release публикует артефакт только после соответствующего bot-dispatched build и проверки, что исходник прошивки не устарел относительно main.

### Что означает release:none

release:none не повышает версию прошивки. После слияния workflow может обновить служебное состояние обработанных PR; детали проверяй по актуальному `release-versioning.yml` и `tools/release_automation.py`. Не редактируй state-файл вручную.

Если post-merge automation упала, изучи доступные результаты и код workflow. Не запускай workflow повторно вручную без прямого разрешения пользователя и не меняй номер версии или `state.json` вручную.

## 5. Синхронизация Web GUI и технических файлов

Исходный HTML/CSS/JavaScript веб-пульта хранится в lego_technic_esp32/web_page.cpp; index.html формируется из встроенного источника. При изменении GUI или ресурсов проверь, что сгенерированные представления актуальны. Версия в интерфейсе и README синхронизируется генераторами, а CHANGELOG.md получается из changelog в app.cpp.

Если CI сообщает, что сгенерированные файлы устарели:

1. Определи, какой файл является источником.
2. Запусти соответствующий генератор.
3. Включи обновлённые производные файлы в тот же PR.
4. Проверь, что повторный запуск генератора не даёт нового diff.

Не исправляй только index.html, CHANGELOG.md или отображаемую версию в README, если источник продолжает генерировать старое содержимое.

## 6. Подходящие локальные команды

Единственная дополнительная ручная программная регрессия перед релизом:

    python3 tools/run_regression_checks.py

Для узкой диагностики можно запускать отдельные тесты или `tools/project_auditor.py`, но не считать их обязательным многоступенчатым процессом. Автоматический CI запускается по триггерам workflow; не запускай Actions вручную. Отчёт должен различать локально выполненные проверки, фактический CI и аппаратные испытания.

## 7. Аппаратные изменения

Код, статический аудит и компиляция не заменяют проверку физической схемы. Для драйверов моторов, питания, делителя напряжения, сервопривода, OLED и I²C требуются:

- подтверждённые GPIO и соединения по фактической схеме;
- проверка диапазонов напряжения и токов;
- контролируемый стендовый запуск с возможностью немедленно отключить питание приводов;
- проверка остановки при потере связи и других значимых отказах;
- обновлённая документация, не выдающая предположения за испытанные факты.

Draft PR, незавершённая компиляция и успешные CI-проверки не являются разрешением подключать моторное питание к непроверенной схеме.
