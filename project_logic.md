# Логика проекта LEGO Technic ESP32

## 1. Общая архитектура

Логика системы построена по цепочке:

**Телефон → Wi-Fi → WebSocket → ESP32 → исполнительные устройства**

Телефон открывает веб-страницу, которую сама ESP32 отдаёт по HTTP. После
загрузки страницы JavaScript устанавливает WebSocket-соединение с `/ws`.

Команды управления передаются в JSON-виде.

Пример:

``` json
{"ch":"A","val":50}
```

где:

-   `ch` --- канал управления;
-   `val` --- значение от `-100` до `100`.

ESP32 принимает команду, определяет текущий режим и передаёт значение
соответствующему исполнительному устройству.

------------------------------------------------------------------------

## 2. Аппаратная структура

### Питание

Основной источник питания --- аккумуляторный блок 2×18650.

Силовая цепь:

``` text
2×18650
   ↓
HX-2S-JH20 BMS
   ↓
выключатель
   ↓
общая силовая шина
   ├──→ Mini360 → 5 В → ESP32
   └──→ TB6612 VM
```

Mini360 используется для получения 5 В для ESP32 и сервопривода.

TB6612 получает силовое питание непосредственно от аккумуляторной шины.

Все устройства имеют общий GND.

### Исполнительные устройства

TB6612 управляет двумя моторными каналами:

``` text
TB6612 канал A → мотор A
TB6612 канал B → мотор B
```

Сервопривод подключён непосредственно к GPIO ESP32 через сигнальную
линию.

OLED SSD1306 подключён по I2C.

Напряжение аккумулятора измеряется через резистивный делитель на ADC
GPIO34.

------------------------------------------------------------------------

## 3. Распределение GPIO

    GPIO Назначение
  ------ ------------------------------
       4 TB6612 STBY
      16 TB6612 AIN1
      17 TB6612 AIN2
      18 TB6612 PWMA
      19 TB6612 BIN1
      21 TB6612 BIN2
      22 TB6612 PWMB
      27 сигнал сервопривода
      25 OLED SDA
      26 OLED SCL
      34 измерение напряжения батареи

Для PWM моторов используются аппаратные LEDC-каналы 4 и 5.

Важно: `LEDC_CH_A` и `LEDC_CH_B` --- это номера аппаратных PWM-каналов,
а не GPIO.

Каналы 4 и 5 выбраны специально из-за использования библиотеки
ESP32Servo, которая сама использует LEDC.

------------------------------------------------------------------------

## 4. Режимы управления

Прошивка имеет два режима:

``` cpp
MODE_TANK = 0
MODE_CAR  = 1
```

По умолчанию используется танковый режим.

Текущий режим сохраняется во flash-памяти ESP32 через `Preferences`.

### 4.1. Танковый режим

В танковом режиме оба моторных канала независимы:

``` text
A → левая гусеница
B → правая гусеница
```

Каждый канал принимает значение:

``` text
-100 ... 0 ... +100
```

где:

-   `+100` --- движение в одном направлении на полной мощности;
-   `0` --- остановка;
-   `-100` --- движение в обратном направлении.

Таким способом реализуется классическое независимое управление двумя
гусеницами.

### 4.2. Классический режим

В классическом режиме:

``` text
A → основной привод
B → дополнительный мотор / механизм
S → рулевой сервопривод
```

Канал `A` управляет движением модели.

Канал `B` остаётся отдельным вспомогательным моторным каналом.

Канал `S` управляет рулём.

------------------------------------------------------------------------

## 5. Управление мотором

Функция `setMotor()` является центральной точкой управления моторными
каналами.

Она принимает:

-   два GPIO направления;
-   номер LEDC PWM-канала;
-   значение `-100..100`.

Алгоритм:

1.  Значение ограничивается диапазоном `-100..100`.
2.  Берётся абсолютное значение.
3.  Оно преобразуется из диапазона `0..100` в PWM `0..255`.
4.  Два входа направления TB6612 устанавливаются в соответствии со
    знаком значения.
5.  На PWM-канал подаётся рассчитанная скважность.

Таким образом:

``` text
значение < 0 → обратное направление
значение = 0 → стоп
значение > 0 → прямое направление
```

PWM:

``` text
0%   → 0
100% → 255
```

Используется частота PWM 5 кГц и разрешение 8 бит.

------------------------------------------------------------------------

## 6. Центральная функция аварийной остановки

`stopAll()` --- единая функция остановки всей модели.

Она:

1.  останавливает мотор A;
2.  останавливает мотор B;
3.  возвращает сервопривод в сохранённый центральный угол;
4.  обнуляет внутренние значения `motorAVal`, `motorBVal` и `servoVal`.

Эта функция вызывается не только кнопкой STOP, но и автоматически при
переходе режима и при срабатывании watchdog.

Это важная часть архитектуры: все критические сценарии остановки
проходят через одну функцию.

------------------------------------------------------------------------

## 7. Safety watchdog

ESP32 не должна продолжать движение модели, если связь с телефоном
оборвалась.

Для этого используется watchdog команд управления:

``` cpp
CMD_TIMEOUT_MS = 500
```

Каждый корректно разобранный WebSocket-пакет обновляет:

``` cpp
lastCmdMillis
```

В основном `loop()` постоянно проверяется:

``` text
текущее время - время последней команды > 500 мс
```

Если прошло больше 500 мс, вызывается:

``` cpp
stopAll();
```

### Зачем нужен постоянный heartbeat

Одного `oninput` недостаточно.

Если пользователь держит слайдер неподвижно, браузер перестаёт
генерировать события изменения значения.

Поэтому JavaScript каждые 150 мс отправляет текущие значения каналов
заново:

``` text
A
B
S
```

Это подтверждает, что соединение живо и управление всё ещё активно.

Получается двухуровневая логика безопасности:

``` text
WebSocket + heartbeat 150 мс
          ↓
ESP32 получает команды
          ↓
watchdog 500 мс
          ↓
нет команд → STOP
```

------------------------------------------------------------------------

## 8. WebSocket-протокол

WebSocket работает по адресу:

``` text
/ws
```

Основной формат команды:

``` json
{"ch":"A","val":50}
```

Возможные каналы:

``` text
A — моторный канал A
B — моторный канал B
S — сервопривод
```

В зависимости от режима значение канала интерпретируется по-разному.

Дополнительно через WebSocket передаются команды конфигурации:

### Переключение режима

``` json
{"mode":0}
```

или:

``` json
{"mode":1}
```

При переключении режима ESP32 сначала сохраняет новый режим и выполняет
`stopAll()`.

### Центр сервопривода

``` json
{"trim":10}
```

`trim` задаёт абсолютное смещение центра относительно 1500 мкс.

Диапазон:

``` text
-400 ... +400 мкс
```

### Максимальный угол

``` json
{"maxdeg":45}
```

Диапазон:

``` text
5 ... 90 градусов
```

------------------------------------------------------------------------

## 9. Управление сервоприводом

Сервопривод работает с частотой 50 Гц.

Основная логика использует положение от `-100` до `+100`, которое
преобразуется в физический импульс.

Формула:

``` text
us = центр + (val / 100) × максимальный угол × (1000 / 180)
```

Центр по умолчанию:

``` text
1500 мкс
```

Максимальный угол по умолчанию:

``` text
45°
```

Итоговый импульс дополнительно ограничивается абсолютным диапазоном:

``` text
500 ... 2500 мкс
```

Это служит дополнительным предохранителем от выхода за безопасный
диапазон управления сервоприводом.

------------------------------------------------------------------------

## 10. Калибровка руля

Калибровка состоит из двух независимых параметров.

### Trim

Позволяет изменить центральное положение сервопривода.

Физический центр рассчитывается как:

``` text
1500 мкс + trim
```

### Max angle

Определяет максимальный угол поворота в каждую сторону.

Оба параметра сохраняются в `Preferences`.

Поэтому после перезагрузки ESP32 калибровка не теряется.

Веб-интерфейс при открытии запрашивает сохранённые значения через:

``` text
GET /calib
```

ESP32 возвращает JSON:

``` json
{
  "trim": 0,
  "maxdeg": 45
}
```

------------------------------------------------------------------------

## 11. Постоянное хранение настроек

Для хранения конфигурации используется библиотека `Preferences`.

Namespace:

``` text
cfg
```

Сохраняются:

``` text
mode     → текущий режим
steer_c  → центр сервопривода
steer_a  → максимальный угол сервопривода
```

Это позволяет не терять настройки после перезагрузки.

------------------------------------------------------------------------

## 12. OLED-дисплей

Используется SSD1306:

``` text
128×64
I2C address: 0x3C
```

Дисплей обновляется примерно раз в секунду.

На нём отображаются:

### Крупная информация

-   текущий режим: `TANK` или `CAR`;
-   процент заряда батареи.

### Техническая информация

-   измеренное напряжение батареи;
-   количество подключённых WebSocket-клиентов.

OLED предназначен прежде всего для локального контроля состояния модели
без телефона.

------------------------------------------------------------------------

## 13. Измерение батареи

Напряжение аккумуляторной шины измеряется через резистивный делитель:

``` text
Battery +
    |
   100k
    |
    +----→ GPIO34
    |
   39k
    |
   GND
```

ADC ESP32 считывает напряжение на средней точке делителя.

Чтобы уменьшить шум, выполняется 8 измерений и используется их среднее
значение.

Для пересчёта ADC в напряжение применяется калибровочный коэффициент:

``` cpp
BATT_DIVIDER_FACTOR = 0.2680
```

Он был скорректирован по фактическому измерению мультиметром.

### Процент батареи

Текущая логика использует пороги:

    Напряжение   Индикация
  ------------ -----------
       ≥ 8.2 В        100%
       ≥ 7.8 В         75%
       ≥ 7.4 В         50%
       ≥ 7.0 В         25%
       ≥ 6.8 В         10%
      \< 6.8 В          0%

Это именно текущая условная индикация уровня заряда, а не точная оценка
остаточной ёмкости аккумуляторов.

------------------------------------------------------------------------

## 14. Wi-Fi

ESP32 сама создаёт Wi-Fi точку доступа:

``` text
SSID: LegoTechnic
IP:   192.168.4.1
```

Телефон подключается непосредственно к ESP32.

Интернет для обычного управления не требуется.

После подключения пользователь открывает веб-интерфейс ESP32.

Это позволяет использовать модель автономно в поле.

------------------------------------------------------------------------

## 15. Веб-интерфейс

HTML, CSS и JavaScript полностью встроены в прошивку в переменную:

``` cpp
PAGE_HTML
```

ESP32 отдаёт эту страницу по адресу:

``` text
/
```

Таким образом, отдельный веб-сервер, приложение или интернет не нужны.

Интерфейс рассчитан прежде всего на телефон в горизонтальной ориентации.

Основные элементы:

-   переключатель режимов;
-   вертикальные слайдеры;
-   кнопки остановки;
-   визуализация направления движения;
-   управление дополнительным мотором;
-   управление рулём;
-   trim руля;
-   максимальный угол руля;
-   полноэкранный режим;
-   отображение IP;
-   индикация ESP32.

------------------------------------------------------------------------

## 16. Логика веб-интерфейса

JavaScript хранит последние значения:

``` javascript
state = {
  A: 0,
  B: 0,
  S: 0
}
```

При изменении слайдера отправляется соответствующая команда.

Одновременно каждые 150 мс выполняется повторная отправка текущих
значений.

Это не только механизм управления, но и часть системы безопасности.

### STOP в интерфейсе

Кнопка STOP вызывает `stopAll()` на стороне JavaScript.

Она сбрасывает управляющие слайдеры в ноль и отправляет нулевые команды.

При этом окончательная аппаратная защита всё равно находится на стороне
ESP32: watchdog способен остановить модель независимо от интерфейса.

------------------------------------------------------------------------

## 17. Переключение режимов

При выборе другого режима:

1.  браузер отправляет команду `mode`;
2.  ESP32 сохраняет новый режим;
3.  ESP32 вызывает `stopAll()`;
4.  веб-интерфейс переключает видимую панель;
5.  управляющие элементы возвращаются в безопасное нулевое состояние.

Это сделано намеренно: при смене типа управления модель не должна
продолжать выполнять старую команду.

------------------------------------------------------------------------

## 18. HTTP endpoints

В прошивке используются следующие основные HTTP/WebSocket точки:

### `/`

Основная HTML-страница управления.

### `/calib`

Возвращает сохранённые параметры рулевого управления:

``` json
{"trim":0,"maxdeg":45}
```

### `/ws`

WebSocket для команд управления.

### `/update`

Веб-интерфейс ElegantOTA для обновления прошивки без USB.

------------------------------------------------------------------------

## 19. OTA-обновление

Для обновления прошивки используется ElegantOTA.

Текущая схема позволяет заменить прошивку без физического подключения
USB:

``` text
новая прошивка
      ↓
.bin
      ↓
ESP32 по Wi-Fi
      ↓
ElegantOTA
      ↓
перезагрузка
      ↓
новая версия прошивки
```

В текущем варианте OTA защищён авторизацией:

``` text
user: admin
pass: admin
```

Эти данные подходят для текущего этапа альфа-тестирования, но перед
передачей модели другим пользователям должны быть заменены.

------------------------------------------------------------------------

## 20. Цикл работы ESP32

После включения выполняется `setup()`.

Последовательность:

1.  запуск Serial;
2.  настройка TB6612;
3.  настройка PWM;
4.  подключение сервопривода;
5.  запуск I2C и OLED;
6.  загрузка сохранённого режима;
7.  загрузка калибровки руля;
8.  запуск Wi-Fi точки доступа;
9.  регистрация WebSocket;
10. регистрация HTTP-маршрутов;
11. запуск ElegantOTA;
12. запуск веб-сервера;
13. первоначальная остановка всех исполнительных устройств;
14. запуск отсчёта watchdog.

После этого работает `loop()`.

В `loop()` выполняются три основные задачи:

``` text
проверка watchdog
       ↓
обновление OLED раз в секунду
       ↓
обслуживание OTA и WebSocket
```

------------------------------------------------------------------------

## 21. Безопасное состояние

Главный принцип управления:

**при отсутствии уверенности в наличии актуальной команды модель должна
остановиться.**

Это реализовано несколькими уровнями:

-   `stopAll()` как единая функция остановки;
-   остановка при смене режима;
-   watchdog 500 мс;
-   heartbeat WebSocket 150 мс;
-   сброс управляющих элементов интерфейса в ноль;
-   возврат сервопривода в центр при остановке.

------------------------------------------------------------------------

## 22. Зависимости и версия ESP32 Core

Текущая прошивка сознательно использует:

``` text
ESP32 Arduino Core 2.0.9
```

Причина --- текущий код использует старый API LEDC:

``` cpp
ledcSetup()
ledcAttachPin()
```

Также проект зависит от конкретной совместимости используемых библиотек
веб-сервера, PWM и OTA.

Поэтому обновление ESP32 Core не должно выполняться автоматически без
проверки сборки.

Текущая рабочая версия прошивки в исходнике:

``` text
0.0.5
```

------------------------------------------------------------------------

## 23. Основные точки, которые нельзя менять без проверки

Следующие элементы связаны между собой и требуют осторожности при
рефакторинге:

### GPIO

Изменение GPIO требует проверки одновременно:

-   аппаратной распайки;
-   TB6612;
-   OLED;
-   сервопривода;
-   делителя батареи;
-   программной конфигурации.

### LEDC channels

Номера LEDC-каналов используются совместно с ESP32Servo.

Изменение каналов требует проверки отсутствия конфликта PWM.

### WebSocket protocol

Изменение формата:

``` json
{"ch":"A","val":50}
```

требует синхронного изменения:

-   JavaScript;
-   `handleWsMessage()`;
-   логики режимов.

### `stopAll()`

Эта функция является центральной частью безопасности.

Изменения в ней нужно проверять особенно внимательно.

### Watchdog

Изменение `CMD_TIMEOUT_MS` должно рассматриваться вместе с периодом
heartbeat JavaScript.

Сейчас:

``` text
heartbeat = 150 мс
watchdog  = 500 мс
```

### Preferences

Имена ключей:

``` text
mode
steer_c
steer_a
```

используются для постоянного хранения конфигурации.

Их изменение может привести к потере ранее сохранённых настроек.

## 25. Принцип развития проекта

При дальнейшем развитии желательно сохранять разделение на уровни:

``` text
Аппаратный уровень
    ↓
управление моторами / серво / ADC / OLED
    ↓
логика модели
    ↓
WebSocket-протокол
    ↓
веб-интерфейс
    ↓
OTA и сборочная инфраструктура
```

Особенно важно не смешивать в одной функции:

-   аппаратное управление;
-   пользовательский интерфейс;
-   сохранение настроек;
-   безопасность.

Это позволит постепенно расширять контроллер, не ломая базовую систему
управления.

## 26. Текущее состояние проекта

Текущая прошивка представляет собой единый монолитный `.ino`, внутри
которого находятся:

-   конфигурация аппаратных пинов;
-   моторная логика;
-   сервопривод;
-   измерение батареи;
-   OLED;
-   Preferences;
-   WebSocket-сервер;
-   HTTP-сервер;
-   HTML/CSS/JavaScript интерфейс;
-   OTA;
-   главный цикл безопасности.

На стадии альфа-тестирования это допустимо и удобно для быстрого
изменения проекта.

При существенном расширении функциональности возможен переход к
разбиению проекта на отдельные модули, но это должно выполняться без
изменения существующего протокола управления и аппаратной распайки без
необходимости.

## 27. Главное назначение этого документа

Этот файл является технической картой прошивки.

Он нужен для того, чтобы при последующих изменениях было понятно:

-   зачем существует конкретная часть кода;
-   какие функции связаны между собой;
-   какие GPIO заняты;
-   как команда из телефона превращается в движение;
-   как работает аварийная остановка;
-   где хранятся настройки;
-   как устроена связь телефона с ESP32;
-   какие части относятся к аппаратуре, а какие --- к интерфейсу.

При изменении прошивки этот документ следует обновлять вместе с
архитектурными изменениями.
